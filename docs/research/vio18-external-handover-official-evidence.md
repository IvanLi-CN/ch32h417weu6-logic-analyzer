# CH32H417 External VIO18 Official Evidence

## Scope

This note uses only WCH's CH32H417 data sheet and WCH's official SDK. It does
not use a reference project, a board test, or inferred reset behavior.

## Evidence

| Question | Official evidence | Conclusion |
| --- | --- | --- |
| What normally drives `VIO18`? | CH32H417 data sheet, Section 1.4.3, page 8: `VIO18` is normally generated by the I/O-pin LDO powered from `VDDIO`. | The normal source is the internal LDO. |
| Can the internal LDO be changed or disabled? | The same section lists software selections 1.2 V, 1.8 V, 2.5 V, 3.3 V, or off. The official PWR SDK exposes `PWR_VIO18ModeCfg()` and `PWR_VIO18LevelCfg()`. | Software control exists, but the public SDK header does not map its `MODE0..MODE5` constants to voltages or off in source comments. Do not select an off enum from inference. |
| What does the `XO` resistor do? | Data sheet Table 3-2: a pull-down on `XO` selects the **internal LDO's** power-up default. 220-400 kOhm selects 2.5 V; 60-110 kOhm selects 1.2 V; 1.2 Mohm through floating selects 1.8 V. | This table does not describe or approve an external-regulator handover. It is not sufficient evidence to add `300 kOhm` for that purpose. |
| Does WCH endorse software VIO adjustment with attached external devices? | Official SDK example [`PWR/SEL_VIO18`](https://github.com/openwch/ch32h417/blob/main/EVT/EXAM/PWR/SEL_VIO18/V3F/User/main.c) states that hardware configuration is recommended to ensure external-device safety. | The official example points away from using an assumed software transition as a safety mechanism for an externally connected circuit. |
| Is `PA5` reset high impedance? | The data sheet identifies PA5 as `PA5/ADC5/OP1_O1/DAC2`; it does not specify PA5's reset electrical state. The SDK DAC example configures PA4 to analog mode only during DAC initialization. | No official source found that guarantees PA5 high impedance during reset. It must not be used as the premise of a passive 2.5-V feedback state. |
| Can DAC data be written before enabling the channel? | The official SDK has separate `DAC_SetChannel2Data()` and `DAC_Cmd()` functions. The write function writes the data-holding register without enabling the channel. | Firmware can write the holding register before `DAC_Cmd()`, but this does not establish PA5's reset state, DAC reset output, or an external-VIO handover guarantee. |

## Design Conclusion

The following proposal is unsupported and shall not be used as an instruction to
modify the schematic:

- add `300 kOhm` from `XO` to GND to coordinate with an external regulator;
- replace the existing EA3036C CH3 feedback network with a DAC injection
  network;
- rely on PA5/DAC2 being high impedance during reset;
- join an external CH3 output and the internal `VIO18` LDO on the assumption
  that equal nominal voltages make the connection safe.

The product requirement for external `VIO18` remains valid. However, an
official WCH application circuit or written vendor confirmation is required
before changing the existing external-VIO18 schematic or defining its
internal-LDO interaction. This is a documentation boundary, not a request for
board testing or a placeholder component.
